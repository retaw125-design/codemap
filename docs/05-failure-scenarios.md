# 05. 장애·예외 시나리오 (PHASE 5)

## 시나리오
| # | 상황 | 원인 | 사용자에게 보이는 것 | 대응 | 재발 방지 |
|---|---|---|---|---|---|
| 1 | DB 연결 안 됨 | Supabase 무료 등급 1주 미사용 일시 정지 | "잠시 후 다시 시도해 주세요" | 대시보드에서 재개 | 배포·테스트 기간 주간 확인 |
| 2 | OpenAI 응답 없음 | 지연, 장애, 한도 초과 | AI 기능만 일시 중지 | 재시도 2회 후 포기 | 연속 실패 시 차단기 |
| 3 | GitHub 요청 거절 | 요청 횟수 제한 | 코드 뷰어 "잠시 후 다시" | 사용자 토큰으로 재요청 | 브라우저 캐시 |
| 4 | 서버 메모리 초과 | 너무 큰 저장소 | 해당 분석만 실패 안내 | 작업 실패 처리 | 내려받기 전 크기 확인, 파일 수 상한 |
| 5 | 이상한 저장소 | 서버 파일을 가리키는 링크, 압축 폭탄 | "분석할 수 없는 저장소" | 즉시 중단 | 링크 건너뛰기, 압축 해제 상한 |
| 6 | 같은 저장소 동시 요청 | 여러 명이 동시에 같은 저장소 입력 | 모두 같은 결과 | 한 번만 분석, 결과 공유 | (repository_id, commit_sha) 유일 제약 |
| 7 | 사용자 몰림 | 커뮤니티 공유 | "대기 중: 앞에 N개" | 순서대로 처리 | 동시 분석 수 제한, 순번 표시 |
| 8 | 키·토큰 유출 | 저장소에 키 커밋, 토큰 탈취 | (보이지 않음) | 즉시 폐기·재발급 | 환경변수만, CI 키 유출 검사 |
| 9 | AI가 이상한 문제 생성 | 없는 노드를 정답으로 지어냄 | 출제되지 않음 | 규칙 검증에서 탈락 | 탈락 비율 기록, 프롬프트 개선 |

## 핵심 원칙
- 부분 동작: 규칙 기능과 AI 기능을 나눠두었으므로, OpenAI가 멈춰도 지도, 빛 효과, 영향 범위 문제는 계속 동작한다.
- 차단기: OpenAI가 연속으로 실패하면 일정 시간 요청을 보내지 않는다.
- 부분 분석: 파일 하나가 파싱에 실패해도 그 파일만 표시하고 나머지는 계속 분석한다.

## 에러 처리
에러 코드 예시
- `ANALYSIS_REPO_TOO_LARGE`, `ANALYSIS_PARTIAL`, `ANALYSIS_UNSUPPORTED_REPO`
- `LLM_UNAVAILABLE`
- `GITHUB_RATE_LIMITED`
- `AUTH_EXPIRED`

응답 형식
| 항목 | 내용 | 누가 봄 |
|---|---|---|
| code | 에러 코드 | 프론트엔드 |
| message | 무엇을 하면 되는지 포함한 한국어 문장 | 사용자 |
| request_id | 요청 추적 번호 | 문의 시 |
| detail | 실제 오류 내용 | 개발 환경에서만 |

로그 기준
- 에러: 사용자가 기능을 못 쓴 경우 → Sentry 알림
- 경고: 재시도 후 성공, 부분 분석 → 기록
- 정보: 단계별 소요 시간, LLM 비용 → README 수치

## 복구
- 평가셋(human_grades)은 다시 만들 수 없는 유일한 데이터다. Supabase 무료 등급은 자동 백업이 없으므로 GitHub Actions로 매주 평가셋과 문제 데이터를 내보내 보관한다.
- 배포 문제 시 Railway에서 이전 버전으로 되돌린다.
- DB 구조 변경은 항상 되돌리기 스크립트와 함께 만든다.
