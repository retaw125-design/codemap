# 03. 아키텍처 (PHASE 3)

## 전체 구성
- 브라우저(React): 패널 UI·코드 뷰어, 2.5D 렌더러·빛 효과, 실시간 재분석, 영향 범위 계산
- 서버(FastAPI): API 라우터, 유스케이스(분석·학습), 분석 파이프라인(백그라운드), LLM 게이트웨이·캐시·차단기
- 데이터·외부: Supabase Postgres(데이터·작업 큐·캐시), GitHub(공개 저장소), OpenAI API
- 공유: tree-sitter 쿼리(추출 규칙), 테스트 케이스

## 핵심 설계 결정
### 1. 추출 규칙을 쿼리 파일로 공유
분석은 서버(처음 분석)와 브라우저(편집 후 재분석) 두 곳에서 일어난다. 각자 코드로 짜면 결과가 어긋난다.
그래서 추출 규칙을 `shared/queries/`의 tree-sitter 쿼리 파일 하나로 만들고 양쪽이 같은 파일을 읽는다.
- 서버: 저장소 전체가 필요한 분석 (파일 간 import 해석)
- 브라우저: 편집된 파일 하나의 재추출 + 모듈 색인을 이용한 그 파일의 import 해석
- 영향 범위 계산은 양쪽에 따로 구현하되, `shared/fixtures`의 같은 케이스로 결과 일치를 검증한다.

### 2. 모듈 색인
서버는 그래프와 함께 모듈 색인(모듈 경로 → 파일 위치)을 내려준다. 사용자가 편집 중 import를 바꿔도
브라우저가 그 파일의 import를 해석할 수 있다.

### 3. 노드 ID 고정
`{상대경로}::{전체이름}`. 이름 변경 판정 규칙은 `04-data-model.md` 참고.

## 영역 나누기
| 영역 | 담당 | 핵심 객체 |
|---|---|---|
| 분석 | 저장소를 가져와 코드 그래프 생성 | 분석 작업, 코드 그래프 |
| 학습 | 문제 출제, 답안, 채점 | 문제, 풀이 기록 |
| 사용자 | 로그인 | Supabase에 위임 |
코드 그래프는 분석 후 바뀌지 않는 스냅샷이다. 문제는 그래프를 ID로 참조만 하고, 채점은 문제를 바꾸지 않는다.

## 계층과 의존 방향
```
api → application → domain ← infrastructure
```
- domain: 그래프 모델, 영향 범위, 레이어 판정, 이름 변경 판정, 채점 규칙. 순수 Python.
- application: 분석 시작, 그래프 조회, 문제 생성, 채점.
- infrastructure: Supabase 저장소, 작업 큐, OpenAI, GitHub 가져오기, 언어 어댑터, 프레임워크 인식기.
- 인터페이스는 저장소와 LLM 게이트웨이에만 만든다.

## 분석 파이프라인
```
크기 확인(GitHub API) → 압축 파일 내려받기 → 언어 감지 → 파싱(언어 어댑터)
→ 함수·클래스 추출(공유 쿼리) → import 해석 → 역할 인식(FastAPI 인식기)
→ 레이어 판정 → 그래프·모듈 색인 저장 → 임시 파일 삭제
```
- 단계마다 소요 시간을 `stage_timings`에 기록한다.
- 파일 하나가 파싱에 실패해도 그 파일만 표시하고 계속 진행한다(부분 분석).

## 비판 후 반영한 것
| 문제 | 반영 |
|---|---|
| 같은 프로세스에서 파싱하면 API가 멈춤. 서버 재시작 시 작업이 영원히 "진행 중" | 파싱은 프로세스 풀, 동시 작업 1~2개, 작업 임대 만료 후 자동 재대기 |
| 편집 중 import를 바꾸면 처리 불가 | 모듈 색인을 내려주고 브라우저가 해당 파일의 import만 해석 |
| "같은 함수" 판별 기준 없음 | 노드 ID 규칙과 이름 변경 판정 규칙 확정 |
| 저장소 가져오기 보안 부족 | 내려받기 전 크기 확인, 압축 파일로 받기, 심볼릭 링크 건너뛰기 |
| 데이터 접근 경로가 두 갈래 | 데이터는 전부 FastAPI 경유, 사용자 토큰으로 DB 접근 |
