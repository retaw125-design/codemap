# 01. 제품 정의 (PHASE 1)

## 한 줄 정의
코드를 읽을 줄은 알지만 구조가 안 보이는 개발 학습자가, 실제 저장소를 2.5D 층 지도로 보며
"어디를 바꾸면 어디에 영향이 가는지" 훈련하는 서비스.

## 대상
- 맞는 사람: 부트캠프 중후반·수료생, 컴퓨터공학과 3~4학년, 입사 0~2년 차 주니어
- 안 맞는 사람: 문법 입문자(너무 어려움), 3년 차 이상(필요 없음)
- 첫 사용자: 국비 과정 동기들

## 제품 비전
코드를 읽기 → 동작을 이해하기 → 쓰기 전에 설계하기

## 사용자 시나리오 (1차)
1. 공개 GitHub 저장소 주소를 넣고 분석 진행률을 본다.
2. 2.5D 층 지도로 구조를 훑어본다.
3. 코드 뷰어에서 코드를 바꿔보면, 영향받는 곳이 지도에서 빛난다.
4. 원본과 편집본을 겹쳐 비교한다.
5. 문제를 풀고(지도에서 건물 클릭 + 이유 작성) 채점과 피드백을 받는다.
6. 다음 접속 때 풀이 기록과 약한 유형을 본다.

## 버전별 범위
| 버전 | 기능 |
|---|---|
| 1차 | 저장소 분석(Python), 2.5D 층 지도, 영향 범위 빛 효과, 코드 편집 → 실시간 영향 표시, 원본 대 편집본 비교, 문제 출제와 채점 |
| 2차 | 실행 흐름 타임라인 재생, AI 실행 예측, 흐름 예측 문제, 설계안 여러 개 비교, 깃 커밋 비교, TypeScript 지원 |
| 3차 | 지도 위 설계 시뮬레이션, 단순 함수 동작 비교 실행, 진짜 3D 탐색 화면, 비유 모드 |

## 문제 유형 (도입 순서)
| 순서 | 유형 | 정답 만드는 법 |
|---|---|---|
| 1 | 영향 범위: "이 함수를 바꾸면 영향받는 파일은?" | 의존 그래프에서 계산 (LLM 불필요) |
| 2 | 기능 추가 위치: "이메일 알림을 추가하려면 어디를?" | LLM 생성 + 노드 존재 여부를 규칙으로 검증 |
| 3 | 버그 추적 | 2차 이후 |

## 1차에서 뺄 것
비공개 저장소, 여러 언어 동시 지원, 회원 간 경쟁·순위, 결제

## 성공 기준
- 배포 링크에서 동기 10명 이상이 실제 저장소로 문제를 풀어봄
- 사람이 채점한 답안 30개 이상과 LLM 채점의 일치율을 측정해 README에 기록

## 시각화 원칙
- 층 = 레이어: 위 API, 가운데 서비스, 아래 DB
- 모양 문법: 클래스는 칸이 나뉜 박스, 함수는 알약, 외부 라이브러리는 책, API는 둥근 입구, DB는 테이블
- 프레임워크 인식기: 코드 패턴으로 역할을 알아내 모양을 입힘 (1차: FastAPI)
- 빛 = 영향 정도: 직접 변경은 강하게, 영향받는 곳은 은은하게, 관련 없는 곳은 어둡게
- 확대 수준별 표시: 멀리서는 폴더 구역, 가까이 가면 클래스의 칸까지
- 코드 뷰어와 지도는 양방향 연결
